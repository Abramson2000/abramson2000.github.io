# RELEASE.md — «Навыки продаж» (crmuro.ru/spin)

## Главное правило

**Любое изменение данных или структуры = новая версия.** Нельзя добавить урок, курс, поле или скрипт
и оставить старый номер. Приложение версионное: вход, скрипты, стили, манифест и service worker
имеют номер в имени файла и кэшируются навсегда. Без нового номера браузер продолжит отдавать
старую сборку, и правка «не появится».

## Как выпускать (пример: 3.2.0 → 3.2.1)

1. Скопировать все версионные файлы с новым номером и заменить номер внутри:
   - `index.3.2.0.html` → `index.3.2.1.html`
   - `app`, `data`, `meddicc-data`, `spiced-data`, `proactive-data`, `boss-gate`,
     `remote-sales-data`, `channel-sales-data`, `management-data` → `*.3.2.1.js`
   - `styles.3.2.1.css`, `manifest.3.2.1.webmanifest`, `supabase.3.2.1.min.js`, `sw.3.2.1.js`
2. В `sw.3.2.1.js` проверить: `VERSION = '3.2.1'`, `ENTRY = './index.3.2.1.html'`,
   и что новые скрипты (например `management-data`) входят в `CORE`.
3. Обновить `sw.js` (безверсионный, его регистрирует страница) — копия `sw.3.2.1.js`.
4. `index.html` — копия `index.3.2.1.html` (это шелл, который открывают напрямую).
5. Проверить: `APP_VER` в `app.3.2.1.js` = 3.2.1; все `script src` в entry указывают на 3.2.1;
   `node --check` для изменённых JS.
6. Закоммитить и запушить. GitHub Pages обновляется 1–10 минут.
7. Проверить живьём: `index.html` содержит 3.2.1, `sw.js` отдаёт VERSION 3.2.1,
   новые файлы — HTTP 200.

## Чего не делать

- Не править `index.3.2.0.html` и другие файлы прошлых версий как «текущие»: это иммутабельные релизы.
- Не добавлять скрипт только в `index.html`: приложение грузит `index.<версия>.html` через service worker.
- Не менять `sw.<версия>.js` без смены версии: байтовое изменение обновит кэш, но номер останется старым.
- Не оставлять `sw.js` от предыдущей версии — иначе браузер продолжит ставить старый релиз.
